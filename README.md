# hertz-API-gateway

## 1\. Overview

### 1.1. Introduction

  * Gateway project: [https://github.com/lar0129/hertz-APIgateway](https://github.com/lar0129/hertz-APIgateway)
  * IDL-Management-Platform frontend project: [https://github.com/wangchunchia/cwg-frontend](https://github.com/wangchunchia/cwg-frontend)
      * For ease of deployment and testing, the IDL-Management-Platform backend is currently coupled with the gateway.
  * Video demonstration: [https://lar0129-video.oss-cn-nanjing.aliyuncs.com/7%E6%9C%8831%E6%97%A5.mp4](https://lar0129-video.oss-cn-nanjing.aliyuncs.com/7%E6%9C%8831%E6%97%A5.mp4)

In a microservices architecture, large services are split into independent microservices, each typically exposing services via RESTful APIs. However, for the client-side, we might need to display data from different microservices on a single page. This necessitates a unified entry point for API calls. **The API Gateway acts as the main entrance for multiple services in this scenario, serving as the system's unified entry point.**

In this project, the API gateway serves as the system's entry point, receiving all incoming HTTP requests, parsing the URL in the request, forwarding them in JSON format to the relevant backend RPC servers, retrieving the responses, and then returning them to the client.

**Technology Stack**

  * Programming Language: golang \>= 1.20
  * API-Gateway Service: Hertz framework, Kitex Client
  * RPC Service: Kitex Service framework
  * Registry Center: etcd
  * RPC Protocol: Thrift

**Advantages**

  * Provides a scalable and reliable solution for large distributed systems, offering a unified external interface.
  * Using an API Gateway allows connection with a microservice registry center, enabling seamless dynamic scaling of microservices.
  * The API Gateway can automatically perform circuit breaking for inaccessible services without manual intervention.
  * As the system's unified entry point, common functionalities across various microservices can be implemented in the API Gateway, minimizing the responsibilities of individual services.
  * The API Gateway helps implement client-side load balancing strategies.

  * The gateway is divided into 5 modules:
      * API Layer (biz/handler package): Accepts HTTP POST requests and passes them to the Routing layer for parsing.
          * Implements **cross-origin** access for any origin, configurable in main.go as needed.
      * Routing Layer (biz/router package and ./router.go): Parses the service name and method name from the URL and decides where to forward the request.
          * **Load balancing** currently uses a weighted random strategy. Can be changed as needed.
      * Kitex Client Provider Layer (biz/clientprovider package): Obtains a generic call client based on the routing result.
          * Achieves **service discovery** through the etcd Registry Center.
          * Parses IDL files via the IDL Provider.
          * Uses **JSON generic calls**, making the gateway highly extensible.
      * IDL Provider Layer (biz/idl/idl\_provider.go file):
          * Sends requests to the IDL Management platform to get the IDL file corresponding to the service name, parses it, and returns the parsed IDL object.
          * When the server-side IDL file changes, a Go routine in the IDL Provider layer **automatically performs IDL-update**.
      * IDL Management Layer (biz/idl/idl\_management.go file):
          * Stores the mapping between [Server Name -- Corresponding IDL Path -- IDL File Description].
          * Provides CRUD functionality for IDL paths.
              * Demonstration video: [https://lar0129-video.oss-cn-nanjing.aliyuncs.com/7%E6%9C%8831%E6%97%A5.mp4](https://lar0129-video.oss-cn-nanjing.aliyuncs.com/7%E6%9C%8831%E6%97%A5.mp4)
          * When adding a new RPC server, simply **add the corresponding service name and IDL file path** to the IDL-management platform to register it with the gateway.
          * Currently only supports IDL files using the **Thrift protocol**.

Optimization Analysis: Go language's built-in profiling tools

  * pprof: Analyze runtime CPU, memory, blocking, and other resource usage.
  * Flame graphs: Identify program hotspots by measuring the relative execution time of different parts for focused optimization.
  * Incremental comparison: Capture two sets of pprof data and compare them to locate issues.
  * Observe threads: Locate issues by observing goroutine stacks.

### 5.2. Specific Optimization Plan

After analysis, the developers identified performance bottlenecks and formulated a specific optimization plan:

  * Reuse Kitex client cache objects in kitex client provider
      * Cache expiration time set to 30min.

```go
var clientCache sync.Map
var cacheTime = make(map[genericclient.Client]time.Time) // Assumes Client type is comparable or pointer

// GetCacheClient Cache the generic call client
func GetCacheClient(serviceName string) (genericclient.Client, error) {
	if cachedClient, ok := clientCache.Load(serviceName); ok {
		oldClient := cachedClient.(genericclient.Client) // Type assertion

		cacheTimeout := 30 * time.Minute
		clientCreationTime, timeOk := cacheTime[oldClient] // Need to store and retrieve creation time

		// Check if the client's creation time exists and if the cache is still valid
		if timeOk && time.Since(clientCreationTime) < cacheTimeout {
			// Cache not expired, return directly
			return oldClient, nil
		}
		// Cache expired, delete old cache entry and its timestamp
		clientCache.Delete(serviceName)
		delete(cacheTime, oldClient) // Remove timestamp entry
	}

	// Cache doesn't exist or expired, create new cache
	newClient, err := InitGenericClient(serviceName) // Assume this function initializes the client
	if err != nil {
		return nil, err
	}
	now := time.Now()
	cacheTime[newClient] = now // Record cache time
	clientCache.Store(serviceName, newClient)
	return newClient, nil
}
```
